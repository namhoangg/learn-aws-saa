In this lab you play two people at once: the **administrator** who creates identities, and **Alice**, a new colleague who signs in with only the permissions you give her. Watching the console from Alice's side is the fastest way to understand implicit deny, inheritance through groups, and the "explicit Deny wins" rule.

> [!WARNING] Use an admin identity, not the root user
> Do the admin steps as an administrator: an IAM Identity Center user, or an IAM user with `AdministratorAccess`. If your account is brand new and you only have the root user, do **Step 1** once as root to create your everyday admin user, then sign out and continue as that user. The root user should already have MFA registered (AWS enforces it within 35 days of the first sign-in).

## Prerequisites

- An AWS account and an identity with administrator permissions (see the warning above).
- A modern browser. The console can keep up to five identities signed in at once in one browser (choose **Turn on multi-session** in the account menu first), so the admin and Alice sessions can sit side by side; a private/incognito window also works.
- Optional, for the CLI tabs: AWS CLI v2 configured as your admin (for example with `aws login`), or **AWS CloudShell** opened from the console as your admin. IAM is global, so any Region works.
- An account created with the standard **Sign up for AWS (advanced)** flow. Accounts from the limited-release "Sign up for AWS (new)" experience cannot give IAM users console access or create an account alias, so Steps 1, 2 and 4 would not work there.
- If you run the CLI tabs from your own machine with an `aws login` profile, add `--profile <name>` to each admin command or run `export AWS_PROFILE=<name>` once; in CloudShell no profile is needed.

## Steps

### Step 1: (Only if you still use the root user) create your everyday admin user

Skip this step if you already sign in as an administrator.

:::console
1. Sign in as the root user and open the **IAM** console.
2. In the navigation pane choose **Users** → **Create user**.
3. On **Specify user details**, enter a **User name** such as `admin-yourname`.
4. Select **Provide user access to the AWS Management Console – optional**, then choose **I want to create an IAM user**.
5. Under **Console password**, choose **Autogenerated password** (or a custom password that you store in a password manager). Keep **User must create a new password at next sign-in (recommended)** selected. Choose **Next**.
6. On **Set permissions**, choose **Add user to group** → **Create group**. Enter **User group name** `Admins`, select **AdministratorAccess** under **Permissions policies**, and choose **Create user group**.
7. Back on **Set permissions**, select the `Admins` group and choose **Next**, then **Create user**.
8. On **Retrieve password**, choose **Download .csv file**. It contains the sign-in URL, user name and password.
9. Sign out of the root user and sign in with the URL from the file as `admin-yourname`. Set a new password when prompted.
:::

:::cli
```bash
# Run as an identity that can manage IAM (CloudShell as root works for this one-off step).
aws iam create-group --group-name Admins
aws iam attach-group-policy --group-name Admins \
  --policy-arn arn:aws:iam::aws:policy/AdministratorAccess
aws iam create-user --user-name admin-yourname
aws iam add-user-to-group --user-name admin-yourname --group-name Admins
# Choose your own strong password; it must meet the account password policy.
aws iam create-login-profile --user-name admin-yourname \
  --password 'Replace-With-A-Long-Unique-Passw0rd!' --password-reset-required
```
:::

> [!CHECK]
> In **Users**, `admin-yourname` shows the `Admins` group on its **Groups** tab, and the **Permissions** tab lists `AdministratorAccess` with **Attached via** the group. If you used the console with the new-password option, you also see `IAMUserChangePassword` attached directly: the console adds it so the user can set that first password.

### Step 2: Give the account a friendly sign-in alias

The sign-in URL contains your 12-digit account ID by default. An alias replaces the number with a word that is easier to remember. Aliases must be 3 to 63 characters of lowercase letters, digits and hyphens, cannot start or end with a hyphen or contain two hyphens in a row, cannot be a 12-digit number, and must be unique across AWS. They are visible in the URL, so do not put anything sensitive in them.

:::console
1. In the IAM console navigation pane choose **Dashboard**.
2. In the **AWS Account** section, next to **Account Alias**, choose **Create** (or **Edit** if one exists).
3. Enter an alias such as `yourname-aws-lab-2026` and choose **Save changes**.
:::

:::cli
```bash
aws iam create-account-alias --account-alias yourname-aws-lab-2026
aws iam list-account-aliases
```
:::

> [!CHECK]
> The Dashboard shows the new alias, and the IAM user sign-in URL now looks like `https://yourname-aws-lab-2026.signin.aws.amazon.com/console`. The old URL with the account ID keeps working.

### Step 3: Create a group with a managed policy

`IAMReadOnlyAccess` is an AWS managed policy that allows `iam:Get*`, `iam:List*` and similar read actions, but nothing that changes IAM.

:::console
1. Choose **User groups** → **Create group**.
2. For **User group name** enter `lab-iam-readers`.
3. Skip the user list for now. In the policy list, search for and select **IAMReadOnlyAccess**.
4. Choose **Create group**.
:::

:::cli
```bash
aws iam create-group --group-name lab-iam-readers
aws iam attach-group-policy --group-name lab-iam-readers \
  --policy-arn arn:aws:iam::aws:policy/IAMReadOnlyAccess
```
:::

### Step 4: Create Alice with no permissions and sign in as her

:::console
1. Choose **Users** → **Create user**. Enter **User name** `lab-alice`.
2. Select **Provide user access to the AWS Management Console – optional** → **I want to create an IAM user**.
3. Choose **Autogenerated password** and clear **User must create a new password at next sign-in (recommended)** to save time in this lab. Choose **Next**.
4. On **Set permissions**, leave **Add user to group** selected but do **not** select any group. Choose **Next**, then **Create user**.
5. On **Retrieve password**, choose **Download .csv file**.
6. Open a second session: choose your account name in the navigation bar → **Add session** → **Sign in** (or use a private window). Sign in with the alias URL, user name `lab-alice` and the password from the file.
7. As Alice, open the **IAM** console and choose **Users**.
:::

:::cli
```bash
aws iam create-user --user-name lab-alice
aws iam create-login-profile --user-name lab-alice \
  --password 'Lab-Alice-Temp-Passw0rd!' --no-password-reset-required
# Sign in as lab-alice in the browser with the alias URL for the next checks.
```
:::

> [!CHECK]
> Alice sees messages saying she is not authorized to perform `iam:ListUsers` (and similar). She has no policies at all, so everything is **implicitly denied**.

### Step 5: Add Alice to the group and try again

:::console
1. In the **admin** session choose **Users** → `lab-alice` → **Groups** tab → **Add user to groups**.
2. Select `lab-iam-readers` and choose **Add user to group(s)**.
3. In **Alice's** session, refresh the **Users** page. Then choose **User groups** → **Create group**, type any name and try to create it.
:::

:::cli
```bash
aws iam add-user-to-group --user-name lab-alice --group-name lab-iam-readers
aws iam list-groups-for-user --user-name lab-alice
```
:::

> [!CHECK]
> Alice can now list users, groups and policies (the group's **Allow** for read actions applies to her), but creating a group fails with an authorization error because `iam:CreateGroup` is not allowed anywhere: still an implicit deny.

### Step 6: Add an inline Deny and watch it override the group

Save this policy as `deny-list-users.json` if you use the CLI, or paste it into the console's JSON editor:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "BlockUserListing",
      "Effect": "Deny",
      "Action": "iam:ListUsers",
      "Resource": "*"
    }
  ]
}
```

:::console
1. In the **admin** session open **Users** → `lab-alice` → **Permissions** tab.
2. Choose **Add permissions** → **Create inline policy**.
3. In the **Policy editor** choose **JSON**, replace the content with the policy above and choose **Next**.
4. Enter **Policy name** `deny-list-users` and choose **Create policy**.
5. In **Alice's** session, refresh **Users**, then open **User groups**.
:::

:::cli
```bash
aws iam put-user-policy --user-name lab-alice \
  --policy-name deny-list-users --policy-document file://deny-list-users.json
aws iam list-user-policies --user-name lab-alice
```
:::

> [!CHECK]
> On Alice's **Permissions** tab the admin sees two entries: `IAMReadOnlyAccess` attached via the group, and the inline `deny-list-users` policy. In Alice's session the **Users** page is denied again, even though the group still allows `iam:List*`, while **User groups** still loads. The explicit **Deny** wins only for the action it names.

### Step 7: Remove the inline policy

:::console
1. In the **admin** session, on `lab-alice` → **Permissions**, select the checkbox next to `deny-list-users` and choose **Remove**, then confirm with **Remove**.
2. In Alice's session refresh **Users**: the list is visible again.
:::

:::cli
```bash
aws iam delete-user-policy --user-name lab-alice --policy-name deny-list-users
```
:::

> [!CHECK]
> The inline policy no longer appears anywhere in the account: inline policies exist only inside their identity, so there is nothing left under **Policies** to clean up.

## Cleanup

Sign out of Alice's session first. Then, as the admin:

- [ ] **Inline policy `deny-list-users`**: already removed in Step 7 (CLI check: `aws iam list-user-policies --user-name lab-alice` returns an empty list).
- [ ] **User `lab-alice`**: console **Users** → select `lab-alice` → **Delete** → type the user name → **Delete** (the console also removes her password and group membership). CLI:
  ```bash
  aws iam remove-user-from-group --user-name lab-alice --group-name lab-iam-readers
  aws iam delete-login-profile --user-name lab-alice
  aws iam delete-user --user-name lab-alice
  ```
- [ ] **Group `lab-iam-readers`**: console **User groups** → select it → **Delete** → type the group name → **Delete**. CLI:
  ```bash
  aws iam detach-group-policy --group-name lab-iam-readers \
    --policy-arn arn:aws:iam::aws:policy/IAMReadOnlyAccess
  aws iam delete-group --group-name lab-iam-readers
  ```
- [ ] **Account alias** (optional, it is free and harmless): **Dashboard** → **AWS Account** section → next to **Account Alias** choose **Delete**, or `aws iam delete-account-alias --account-alias yourname-aws-lab-2026`. Afterwards only the account-ID sign-in URL works.
- [ ] **Downloaded `.csv` files**: delete the Alice credentials file from your computer; move the admin file's password into a password manager and delete the file.
- [ ] **Your admin user `admin-yourname` and group `Admins` (Step 1)**: keep them for the rest of the course and protect the user with MFA in lab 02. Delete them only when you stop using the account or move to IAM Identity Center.
- [ ] Final check: **Users** lists no `lab-` users and **User groups** lists no `lab-` groups (`aws iam list-users --query "Users[].UserName"`).
